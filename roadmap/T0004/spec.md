# Spec: T0004 Theme contrast layer (`ui-theme-overrides.css`) and palette rework

## Restate of intent

- **Outcome:** A generated, per-theme stylesheet `ui-theme-overrides.css` exposes a
  `--color-on-*` variable for every colored role (the text color to use on that
  background). Components consume those variables, so a poor palette cannot break a
  variant. The eight bundled themes are reworked for contrast, type scale, and palette.
- **User:** AI agents first. They must be able to author a theme and trust that
  components stay legible. Humans second.
- **Why now:** Component variants hardcode foregrounds (`--color-text-ondark`,
  `--color-surface-dark`). A theme with a light accent or a mid-gray warning breaks
  them. The token contract has no answer for "which text color goes on this background".
- **Success:** Every colored role has a generated `--color-on-*` that meets WCAG AA
  against its background. No component hardcodes a foreground on a colored background.
  All eight themes pass the contrast and type-scale tests. Generated files never drift.
- **Constraint:** The fixed token list does not change. No runtime JavaScript resolves
  contrast. Styling stays token-only.
- **Out of scope:** New design tokens, a palette editor, per-component override rules
  beyond the `--color-on-*` layer, and themes outside `demos/radix-ui-starter/themes/`.

## Objective

Today a UI component decides its own foreground. For example `Button` sets
`color: var(--color-text-ondark)` for `primary`, `success`, `warning`, `danger`, and
`info`, and `color: var(--color-surface-dark)` for `accent`. `Avatar` sets
`color: var(--color-text-ondark)` on `--color-brand-secondary`. The composer send
button and the user message bubble set `--color-text-ondark` on `--color-surface-dark`.
These choices assume the background is dark. A theme with a light accent or a pale
warning color makes the label unreadable.

T0004 introduces a **derived contrast layer**:

- A generator reads each theme's palette and computes, for each colored role, which of
  the theme's two text colors has the higher WCAG contrast ratio against that role. When
  neither reaches AA, it falls back to pure black or white, so a label stays legible even
  when a theme has no usable dark ink.
- It writes the result to `themes/<name>/ui-theme-overrides.css` as a `--color-on-*`
  variable.
- Components consume `var(--color-on-<role>, <fallback>)`, so they never choose a
  foreground again.

`--color-on-*` variables are **not design tokens**. They never appear in `DESIGN.md`
front matter or in the fixed token list. They are a generated companion layer, like
`color-variants.css`, but per theme.

## Deliverable: `ui-theme-overrides.css`

- **Location:** `demos/radix-ui-starter/themes/<name>/ui-theme-overrides.css`, next to
  `DESIGN.md` and `design-tokens.css`.
- **Generated:** The file carries a header comment that says it is generated and must
  not be edited by hand.
- **Shape:** one `:root` block of `--color-on-*` variables, each a reference to
  `var(--color-text)` or `var(--color-text-ondark)`.

| Variable | Background role |
|----------|-----------------|
| `--color-on-primary` | `colors.brand.primary` |
| `--color-on-accent` | `colors.brand.accent` |
| `--color-on-secondary` | `colors.brand.secondary` |
| `--color-on-tertiary` | `colors.brand.tertiary` |
| `--color-on-success` | `colors.action.success` |
| `--color-on-info` | `colors.action.info` |
| `--color-on-warning` | `colors.action.warning` |
| `--color-on-danger` | `colors.action.danger` |
| `--color-on-dark` | `colors.surface.dark` |

Example output:

```css
/* GENERATED by tools/generate-theme-overrides.ts. Do not edit by hand. */
:root {
	--color-on-primary: var(--color-text-ondark);
	--color-on-accent: var(--color-text);
	--color-on-secondary: var(--color-text-ondark);
	--color-on-tertiary: var(--color-text);
	--color-on-success: var(--color-text-ondark);
	--color-on-info: var(--color-text-ondark);
	--color-on-warning: var(--color-text-ondark);
	--color-on-danger: var(--color-text-ondark);
	--color-on-dark: var(--color-text-ondark);
}
```

## Generator

- **Tool:** `tools/generate-theme-overrides.ts`, run with
  `bun run generate:themes` (a new root script).
- **Input:** each theme's `DESIGN.md` front matter, which is the source of truth for
  token values. Parse it with the `yaml` dependency, as `contract.test.ts` does.
- **Selection rule:** for each role, compute the WCAG 2.1 contrast ratio of
  `colors.text.base` and `colors.text.ondark` against the role color. Pick the one with
  the higher ratio. Tie goes to `colors.text.ondark`. When the chosen ratio is below
  4.5:1, fall back to pure black or white, whichever contrasts more. This is common on
  dark themes whose two text tokens are both light.
- **Output:** overwrite `themes/<name>/ui-theme-overrides.css` for every theme.
- **Pure core:** export `renderThemeOverrides(theme)` so a test can regenerate the text
  in memory. Keep the file writing in a thin `main` guard.

## Theme rework

The eight themes must meet a measurable bar. Adjust a palette only where a check fails.

- **Contrast (WCAG AA):**
  - `colors.text.base` on `colors.surface.base`: at least 4.5:1.
  - `colors.text.muted` on `colors.surface.base`: at least 4.5:1.
  - `colors.text.ondark` on `colors.surface.dark`: at least 4.5:1.
  - Every generated `--color-on-*` against its background role: at least 4.5:1.
  - `colors.brand.secondary` on `colors.surface.base` (UI border): at least 3:1.
- **Type scale:** every theme uses the same `--font-size-*` steps and the sizes never
  decrease from `xs` to `display`. Today `paper` sets `xs` to `0.875rem` and `sm` to
  `1rem`, and the scales differ across themes.
- **Palettes:** keep each theme recognizable. Change a color only to pass a check.

The type sizes live only in `design-tokens.css`, not in the front matter. Normalizing
them does not change the token contract.

## Tech stack

- **Runtime and bundler:** Bun, as today. The generator is TypeScript run by Bun.
- **Parsing:** `yaml` (already a root devDependency).
- **Styling:** plain CSS with `var()`. No new runtime dependency.

## Code style

The generated file is data, not hand-written code. Component CSS consumes the layer with
a fallback, so the library still works when a theme has no generated file:

```css
&.ui-button--primary {
	background: var(--color-brand-primary);
	color: var(--color-on-primary, var(--color-text-ondark));
}

&.ui-button--accent {
	background: var(--color-brand-accent);
	color: var(--color-on-accent, var(--color-text));
}
```

Consumers:

- `ui/Button` — `primary`, `accent`, `success`, `warning`, `danger`, `info` use their
  `--color-on-*`. `secondary` and `ghost` keep `--color-text` on a surface background.
- `ui/Avatar` — fallback uses `--color-on-secondary`.
- `chat/Composer` — send button uses `--color-on-dark`.
- `chat/Message` — the user bubble uses `--color-on-dark`.

## Testing strategy

- **Drift test** (`tools/generate-theme-overrides.test.ts`): for every theme,
  `renderThemeOverrides(theme)` equals the committed `ui-theme-overrides.css`. A
  hand-edit or a stale file fails `bun test`.
- **Contrast test** (`tools/generate-theme-overrides.test.ts`): for every theme and every
  role, the chosen text token meets 4.5:1 against the role color. This is the test that
  forces the palette rework.
- **Type-scale test** (`src/lib/theme/type-scale.test.ts`): every theme defines the same
  `--font-size-*` steps and the values do not decrease across the scale.
- **Token contract** (`contract.test.ts`): unchanged. It keeps `DESIGN.md` and
  `design-tokens.css` identical. Add one assertion that every theme has a
  `ui-theme-overrides.css`.
- Component rendering tests stay out of scope, as documented.

## Boundaries

- **Always:** regenerate after any palette change; keep `DESIGN.md` and
  `design-tokens.css` identical; consume tokens with `var()`; run `bun run check`,
  `bun run typecheck`, and `bun test` before committing.
- **Ask first:** changing the fixed token list or the canonical
  `skills/design-system-tokens/SKILL.md`; changing a contrast target; adding a
  dependency.
- **Never:** add `--color-on-*` to `DESIGN.md` front matter or the fixed token list;
  hand-edit a generated file; write raw colors, sizes, or radii in component CSS; add a
  runtime contrast resolver.

## Success criteria

- [ ] Every theme has a generated `themes/<name>/ui-theme-overrides.css` with the nine
      `--color-on-*` variables.
- [ ] The generator is deterministic and the drift test passes for all themes.
- [ ] Every generated on-color meets 4.5:1 against its role background.
- [ ] The eight themes meet the contrast bar for base, muted, ondark, and UI borders.
- [ ] Every theme uses the same, non-decreasing `--font-size-*` scale.
- [ ] `Button`, `Avatar`, `Composer`, and `Message` consume `--color-on-*` with
      fallbacks, and no component hardcodes a foreground on a colored background.
- [ ] The fixed token list and `DESIGN.md` front matter schema are unchanged.
- [ ] `bun run check`, `bun run typecheck`, `bun test`, and the demo build pass.

## Open questions

1. Generator input: `DESIGN.md` front matter (recommended, it is the source of truth) or
   `design-tokens.css` (simpler to parse)? Recommendation: front matter, reusing `yaml`.
2. Muted text target: 4.5:1 for strict AA (recommended) or 3:1 as a documented
   secondary-text exception? Recommendation: 4.5:1.
3. Should the canonical `skills/design-system-tokens/SKILL.md` document the derived
   layer as a reusable pattern? Recommendation: yes, a short section, without changing
   the fixed token list.
4. Should the generator also emit a comment with each computed ratio, to make review
   easier? Recommendation: yes, one comment line per role.
